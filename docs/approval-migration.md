# Approval Inbox migration runbook

Approval Inbox schema 2 adds durable requester and settler identities plus an
atomic separation-of-duty invariant. Populated schema-1 SQLite inboxes migrate
only through an explicit, offline, backup-first operation.

## Preconditions

1. Stop every process that can submit, settle, orphan, or read/write the inbox.
2. Confirm the source is the intended Approval Inbox database.
3. Choose a backup path on durable storage. The final path must not exist,
   must differ from the source, and its parent directory must already exist.
4. Ensure both filesystems have free space. Preflight requires the compact live
   SQLite pages plus 1 MiB on the backup filesystem and at least 1 MiB of
   working space beside the source.
5. Keep the old binary stopped until migration or rollback is complete.

## Run

```bash
yh approval-migrate \
  /absolute/path/approval.db \
  /absolute/path/approval-v1.rollback.db
```

The success report states the source and target schemas, historical record
count, number of pending requests orphaned, disk-space observations, and the
rollback backup path.

The command:

- validates every schema-1 body and its approval/thread/turn/status/revision
  indexes before creating a backup;
- creates a compact SQLite backup without overwriting an existing path;
- binds the backup to the complete record set with a streaming SHA-256
  fingerprint and validates `integrity_check`;
- rechecks the source fingerprint under an immediate transaction;
- rewrites records in bounded pages and commits writer metadata atomically.

## Identity treatment

Schema 1 did not record authenticated actors, so migration never invents them.

- Pending requests become `orphaned` with a migration reason and a new
  settlement timestamp. They must be regenerated by a current Runtime if the
  operation is still needed.
- Existing settled decisions remain settled. Their requester and deciding actor
  are explicitly `unattributed_legacy`.
- Existing orphan records remain orphaned and their requester is explicitly
  `unattributed_legacy`.

Current APIs reject `unattributed_legacy` for new requests or settlements.

## Retry after interruption

Rerun the same command with the same source and backup.

- Before backup publication, the source remains legacy and unchanged.
- After publication, the command validates and reuses the exact backup.
- Before source commit, SQLite rolls back all record and metadata changes.
- After commit, rerunning reports that schema 2 is already current and does not
  replace or require the backup.

A uniquely named `.partial-<id>` file can remain after process or machine loss.
It is not the rollback artifact. Confirm that the final backup validates or
that the source remains legacy before removing an orphan partial file.

## Rollback and downgrade

The schema-1 backup is the rollback boundary. Before any schema-2 process
submits or settles a new record, stop all writers and restore the backup
atomically with its required ownership and permissions.

After schema-2 writes occur, restoring the backup discards those newer records
and decisions. That is data-loss recovery, not a supported rolling downgrade.
Schema-1 and schema-2 writers must never share one database concurrently.

Keep the migration success output, backup, release version, and operator change
record according to local retention policy. Y-Harness does not yet implement
legal hold or automatic Approval Inbox retention.
